# PostgreSQL Persistence Strategy

Kiva should use PostgreSQL as the primary persistence backend.

## Decision

Use relational tables for governed state and PostgreSQL `json` for Statement
payloads and authority. This preserves escaped U+0000, which `jsonb` rejects.
SQLx binds these payloads as JSON text cast directly to `json`, bypassing its
default `jsonb` parameter type. xAPI document bodies and Agent objects also use
`json`; arbitrary document identifiers, canonical keys and actor IFIs use UTF-8
`bytea` because PostgreSQL `text` cannot represent U+0000. Other structured
records retain their existing `jsonb` representation. Manage schema change with
Atlas versioned migrations and access PostgreSQL from Rust through SQLx.

This is a better fit than a document database as Kiva moves beyond a simple LRS
into a Personal Data Store, BI substrate, and policy-governed public-use
platform. Kiva needs transaction boundaries, constraints, isolation, audit
indexes, tenant and subject partitioning, document ETags, and controlled schema
evolution. The fact that xAPI payloads are JSON does not mean the whole system
should be schemaless.

## Migration Management

Kiva follows the same migration model as Aegaeon:

- `atlas.hcl`: Atlas environment configuration.
- `db/schema.sql`: desired PostgreSQL schema state.
- `db/migrations/*.sql`: versioned SQL migrations.
- `db/migrations/atlas.sum`: Atlas migration directory integrity hash.
- SQLx: Rust runtime database access.

Atlas owns migration planning and checksum validation. SQLx owns runtime query
execution from Rust. The application should not generate schema changes at
runtime.

## Schema Shape

The current desired schema lives in `db/schema.sql` and the versioned migration
history under `db/migrations/`.

Statements should store:

- `tenant_id` and `statement_id` as the durable identity boundary.
- Promoted searchable fields such as actor IFI, verb IRI, object IRI, stored
  timestamp, version, authority, and voiding reference.
- The accepted Statement JSON as `json`. Filtering uses promoted metadata or
  decoded Rust values; the former Statement GIN index is removed by migration
  `20261026000000_xapi_json_and_sha2.sql`.

The same migration allows full SHA-224/256/384/512 attachment digests, matching
`IP-Attachment-sha2-value` and the test ledger's FIPS 180-2 dependency contract.
Existing Statement JSON values and attachment rows survive the migration.

Attachment part Content-Type fields use UTF-8 `bytea` after migration
`20261029000000_xapi_attachment_media_bytes.sql`. The adopted MIME grammar
allows ASCII NUL inside comments, quoted strings and quoted pairs, which
PostgreSQL `text` cannot store. The migration converts existing text to its
unchanged UTF-8 bytes, including the empty marker for an absent optional header.
Reads validate UTF-8 and preserve the accepted field and raw payload bytes.

Supplied Statement and SubStatement timestamps retain leap-second markers and
their decimal fractions when projected to UTC. Replay comparison uses the same
lossless projection for explicit SubStatement timestamps. Values already
collapsed to `:59.999999999` by older writes cannot be recovered from stored JSON.
The current timestamp wire profile uses UTC RFC3339 years `0000` through `9999`.
Conversion and formatting are checked independently: local timestamps whose UTC
instant falls outside that wire range receive `400` before any Statement is
stored, including every member of a POST batch. This is a representation limit,
not a newly selected future-clock margin or a claim of full ISO 8601 support.

Document `since` bounds are compared as instants, including local RFC3339 inputs
whose UTC year crosses that Statement wire range. PostgreSQL binds an integer
day/microsecond interval from the Unix epoch and applies it in UTC, avoiding the
driver's unchecked calendar conversion. Flooring finer fractions preserves the
exclusive comparison with microsecond stored times, including before the epoch;
the query does not depend on the database session time zone.

Document resources should store:

- A canonical `document_key` generated by the application from the xAPI resource
  scope.
- Resource kind, document id, Activity id, Agent JSON, registration, ETag,
  content type and raw document bytes. New HTTP PUTs retain every entity octet,
  including JSON whitespace, repeated members and content-type parameters.
  The existing `content_json` column remains readable for legacy rows; new
  representations use `content_bytes` without a schema migration.

Only POST merge requires both representations to be JSON Objects. It replaces
top-level properties while retaining each nested value's raw JSON and exact
number tokens; malformed/non-object or non-JSON input leaves the existing
representation, ETag and update instant unchanged. PUT may store an arbitrary
entity even when its declared media type is JSON. Bytes already lost by an older
parsed-JSON write cannot be reconstructed from that historical row.

Migration `20261027000000_xapi_document_unicode.sql` preserves existing rows
while converting these document/IFI columns. Account names escape percent and
colon in canonical keys so different homePage/name pairs cannot collide; the
migration rebuilds affected persisted keys. Document writes hold a transaction
advisory lock for the tenant/resource kind across the precondition read and
write, including missing rows and bulk State deletion. Concurrent If-Match
updates cannot both succeed, and disjoint JSON POST merges retain both updates.

Confidential workflow state should store:

- participant lifecycle metadata and participant audit events;
- Additive share signing-key registrations and submitted-share metadata under a
  subject and tenant boundary.
- Accepted additive-share replay records with database uniqueness constraints.
- Computed aggregate results that can be used as evidence for release requests.
- Two-authority threshold-release requests, approvals, and release timestamps.
- Shamir threshold-reconstruction metadata, including verification profile,
  verified share counts, complaint counts, and the reconstructed field element;
  metadata-list and PDS data-product responses do not return submitted share
  values or reconstructed values.
- Subject-owned differential privacy budget ledgers with bounded total, spent,
  and remaining epsilon microunits.
- Differential privacy noised aggregate release evidence bound to a subject
  budget, a computed aggregate result, a recorded noise sample, and the
  resulting noised value.
- Confidential job lifecycle metadata, quotas, idempotency keys, deadlines,
  state transitions, and job audit events.

PDS workflow state should store:

- consent grants, revocation metadata, and access-audit events;
- approved data products with source-kind-specific references to completed
  threshold releases, persisted differential-privacy releases, and persisted
  Shamir threshold-reconstruction metadata. Application code should resolve
  those references through the `ReleaseArtifactAvailabilityPort` boundary so
  PDS logic depends on governed artifact availability rather than on each
  confidential mechanism table directly;
- subject-facing lifecycle events, retention policies, lifecycle cases, and
  public-sector governance profiles.

The application should derive promoted columns from accepted xAPI payloads, not
trust clients to supply them separately.

## OAuth 2.1 Boundary

Kiva behaves as an OAuth 2.1-style resource server at the xAPI, PDS, and
confidential-computation HTTP boundaries:

- Bearer credentials are accepted through the `Authorization` header.
- Query-string access tokens are rejected.
- Token validation, introspection, audience checks, and scope-to-policy mapping
  remain deployment-adapter concerns rather than xAPI payload validation.
- Accepted bearer tokens are mapped to an internal authenticated principal with
  an OAuth/OIDC-derived subject and an exact set of Kiva resource-server scopes.
- xAPI requests enforce `xapi:read` or `xapi:write` when a bearer token is
  presented, and always enforce them when `KIVA_REQUIRE_AUTHORIZATION=true`.
- PDS and confidential-computation requests require bearer tokens and exact
  `pds:*` or `confidential:*` operation scopes.

This is the current resource-server enforcement boundary. It does not implement
production token validation, JWKS verification, introspection, refresh-token
flows, or tenant-specific claim transformation.

## Migration Path

The server keeps in-memory stores for lightweight conformance smoke tests and
uses PostgreSQL for Statement and xAPI document operations when `DATABASE_URL`
is configured. State, Agent Profile, and Activity Profile resources share the
same repository boundary and store JSON documents in `kiva.xapi_documents` with
ETags and update timestamps. Confidential workflow stores use the same
repository boundary for signing keys, submitted shares, replay records, computed
aggregates, threshold releases, differential privacy budget ledgers, and
differential privacy noised aggregate releases.

Database-backed LRS conformance is captured by
`scripts/ci/run_postgres_conformance.sh`. The
script initializes a disposable PostgreSQL cluster under `/tmp`, applies all
versioned migrations, starts `kiva-server` with `DATABASE_URL`, and runs the
bundled HTTP conformance suite with the endpoint and authentication fixtures
needed for the profile-sensitive cases.

```sh
scripts/ci/run_postgres_conformance.sh
```

PostgreSQL-specific confidential workflow checks live in
`scripts/ci/run_postgres_verification.sh`. That script applies the same
versioned migrations and runs ignored Rust tests for database-backed invariants
that should not require PostgreSQL during ordinary unit tests.

The current PostgreSQL verification checks include threshold-release idempotence
under duplicate requests and serialized spending from a subject-owned
differential privacy budget ledger. They also check that concurrent duplicate
differential privacy noised release requests are idempotent and spend the
subject-owned budget once.

```sh
scripts/ci/run_postgres_verification.sh
```

Both scripts choose free local ports by default. Conformance ports can be pinned
with `KIVA_POSTGRES_CONFORMANCE_PORT`,
`KIVA_POSTGRES_CONFORMANCE_KIVA_PORT`, or
`KIVA_POSTGRES_CONFORMANCE_ADDR`. Verification can pin PostgreSQL with
`KIVA_POSTGRES_VERIFICATION_PORT` when a CI job needs fixed addresses.

## Runtime Configuration

The server selects its Statement and document stores from environment
configuration:

- If `DATABASE_URL` is unset, `kiva-server` uses in-memory stores. This is
  intended for lightweight local smoke tests and early conformance runner work.
- If `DATABASE_URL` is set, `kiva-server` connects through SQLx and stores
  Statements in `kiva.xapi_statements` and document resources in
  `kiva.xapi_documents`. Confidential workflow state is stored in the
  corresponding `kiva.confidential_*` and `kiva.pds_*` tables.
- `KIVA_TENANT_ID` selects the tenant boundary for stored xAPI resources and
  defaults to `default`.
- `KIVA_REQUIRE_AUTHORIZATION=true` makes normal xAPI resources reject
  anonymous requests with `401 Unauthorized`. `/about` remains available for
  discovery, while malformed bearer credentials and query-string access tokens
  are still rejected.

Atlas migrations are applied outside the application process. A local developer
database should be prepared before starting the server with `DATABASE_URL`:

```sh
atlas migrate apply --env local
DATABASE_URL=postgres://kiva:kiva@localhost:5432/kiva \
  KIVA_TENANT_ID=local \
  KIVA_REQUIRE_AUTHORIZATION=true \
  cargo run -p kiva-server
```

The application should fail closed when the configured database is unavailable
rather than silently falling back to in-memory storage.
